# Catalog audit round 4 — adversarial benchmark register (2026-08-23)

Scope: everything round 3 was generous to itself about, removed. A teardown+reinstall of the same
27-selector TypeScript set as rounds 2/3 (like-for-like diff, this repo), **plus** a first-ever
Copilot install into a synthetic external consumer project (attacks F17's confound at the root,
tests the Copilot adapter's actual output for the first time in any round), **plus** a positive
recall-control (seeded defects in a scratch copy, scored `found/planted` per agent instead of only
verifying precision), **plus** a wider 8-agent panel including a head-to-head between
`ts-code-reviewer` and the generic `shared/code-reviewer` fallback, **plus** a hard rule that every
finding gets fixed and a guard is left behind. Full methodology:
`docs/decisions/catalog-benchmark-audit-2026-08-23.md`.

**Reading the result honestly:** the panel's generalist, `ts-code-reviewer`, had the best raw recall
of the round — it independently caught 5 of the 7 relevant seeds in one pass, including both
misses from the two specialists nominally responsible for them. This is not evidence
`ts-security-auditor`/`ts-performance-profiler` are badly designed in general (round 3 and this
round's real-repo passes both got substantive, correct, on-scope findings from them) — it is
evidence their **search breadth** under this prompt sampled a subset of the tree rather than
exhaustively covering every guard-site/file, missing a defect square in their own stated lane. Two
concrete, catalog-actionable fixes follow from this:

- `ts-security-auditor`'s body should explicitly instruct: "when verifying a `FORBIDDEN_KEYS`-style
  guard, check every merge/assign call site individually, not a representative sample" — the exact
  instruction that would have caught seed #2.
- `ts-performance-profiler`'s body should explicitly instruct exhaustive small-file coverage, not
  just the files that look "central" to data scaling by name/import graph — the exact instruction
  that would have caught seed #6.

Neither agent's `description` needs a scope change — both stayed correctly inside their stated
boundary. This is a body-instruction-depth issue, not a dispatch-trigger issue.

## Head-to-head: `ts-code-reviewer` vs. `shared/code-reviewer`

Both dispatched at identical scope (real repo `src/`). `shared/code-reviewer` (no project-specific
convention rules loaded) independently found 5 real, valid findings (F37's `cli-helpers.ts`
cohesion note plus F44–F47) — genuinely useful, comparable in depth to `ts-code-reviewer`'s
Medium/Low tier. But `shared/code-reviewer` did **not** catch F33/F34 (the two real Medium bugs in
`move/execute.ts`'s rename fallback) that `ts-code-reviewer` did — the project-specific reviewer
earned its place on this pass by finding real bugs the generic fallback missed, not just by finding
more total items.
