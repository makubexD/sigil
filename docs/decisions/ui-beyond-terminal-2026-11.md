# UI beyond the terminal: a generated artifact index, no site or server (2026-11-02)

The brief (`docs/ideas/ui-beyond-terminal.md`, closed by this record) asked whether sigil should offer something people
can use outside a terminal. The decision: build no website, server or extension. Generate one Markdown index of the
catalog's artifacts, committed and checked for staleness like `catalog/README.md`. GitHub renders it, and every row shows
the `sigil add` command.

## Who the audience is

Every way to install an artifact ends in a terminal or in an AI tool's own UI:

- `sigil add` and the wizard are a CLI (`src/wizard/`, `isInteractiveTTY()`).
- The plugin channels already have a graphical browser, run by the tool vendor. In Claude Code, `/plugin` opens a
  Discover tab that lists and searches the plugins of every registered marketplace, with a details pane listing what a
  plugin installs ([Install and manage plugins](https://code.claude.com/docs/en/discover-plugins)). sigil already
  publishes that marketplace. Cursor lists plugins in its Customize panel and at cursor.com/marketplace
  ([Cursor plugins](https://cursor.com/docs/plugins)). Antigravity installs the plugin folders `sigil build` writes
  (`docs/setup/antigravity.md`).

So "people who never open a terminal" are served by the plugin channels, and the way to reach more of them is more
plugin channels (Cursor Phase F), not a sigil UI. A page whose command must still be pasted into a terminal doesn't help
them. That was the brief's riskiest assumption, and it holds.

What is left is "people choosing artifacts": someone reading the repo on GitHub who wants to see what exists, which pack
holds it, which targets get it, and the command to install it. Today they have `sigil list` / `sigil search` (CLI only),
`catalog/README.md` (the authoring standard, not the artifacts) and the catalog folders. A plugin browser lists each pack and what it installs,
but only for its own tool, and never one artifact across packs and targets with the command to install it.

## Options

| Option                             | Effort                                                                | Audience it reaches                                         | Maintenance                                                                                      | Adds over today                                                         |
| ---------------------------------- | --------------------------------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| Generated Markdown index (chosen)  | Small: one generator, one stale test, the `catalog/README.md` pattern | Anyone reading the repo or the npm page; no hosting         | Regenerated by `npm run build`; a test fails when stale                                          | One cross-target view: artifact, pack, targets, install command         |
| Static site (GitHub Pages from CI) | Medium: generator, HTML/CSS, search, a Pages workflow                 | Same people as the index, plus search                       | A second renderer, a deploy job, a web surface to keep accessible and secure; Pages is off today | Search and filtering, over the same data                                |
| Local `sigil serve` page           | Medium: an HTTP server, the CLI's first, plus a page                  | People who already installed the CLI, so already in a shell | A server's security surface (binding, paths), against the trust model of a file-writing tool     | Little: those users have `sigil list`, `search`, `get` and the wizard   |
| VS Code extension                  | Large: a second package, its own release, marketplace review          | VS Code users; Cursor and Antigravity forks partly          | A second product with its own versioning                                                         | An in-editor picker, which each AI tool's plugin panel already provides |
| None                               | None                                                                  | n/a                                                         | None                                                                                             | Nothing                                                                 |

## The spike

A throwaway script (not committed) read `dist/registry.json` and `packs.yaml` and wrote one Markdown table per kind:
artifact id, description, packs, targets, and `sigil add <kind>:<id> --target <t>`.

- 167 artifacts (164 without templates) gave 202 lines and 50 KB in about 12 ms.
- `sigil add skill:shared/feature --target cursor --yes` installs with exactly that id form, so the command column is
  right.
- **The registry can't give pack membership.** 5 of the 14 packs are `languages: [<lang>]` packs, so reading `artifacts:`
  lists left 140 artifacts with no pack. The generator needs sigil's own pack expansion, not the registry. That is a
  reason to generate from the resolved catalog inside `npm run build`, not from `registry.json`.
- One flat page is long but readable. Split by kind or by pack if it grows.

## What stays out

No hosting, accounts or editing in a browser (the brief's own limits). A static site stays possible later: it could
render the same data, and nothing in the index blocks it. Reconsider it only if people ask for search the GitHub page
can't give.
