I asked the ts-code-reviewer agent to review `src/orders.ts`. Its findings hold up against the file, which is 55 lines. Nothing was compiled, tested or run: there's no `node_modules` and no `test/` directory, and the permission system blocked the agent's probe scripts. All findings come from reading the code. I made no edits.

### High
1. **A failed page fetch quietly returns partial totals** (`src/orders.ts:44-47`). The `catch` sets `page = null` and logs at `info`, but only if a logger was passed. The function then returns totals for the pages it got before the failure, so a timeout on page 3 of 10 gives the caller an incomplete total that looks complete. This breaks the project rule against swallowing errors (`.claude/rules/typescript-ts-code-quality.md`). Fix: let the error propagate, or rethrow it with `{ cause }`. If partial results are wanted, return an explicit `complete: false` flag. A name-lookup failure on line 52 already rejects the whole call, so the function has two different failure policies.
2. **Totals are grouped by display name, not `customerId`** (`:18`, `:52`). Two different customers named "John Smith" get one combined total. A customer whose name lookup returns different strings (a rename, different spacing) gets split across rows. The `OrderAggregator` interface (`:9`) passes only the name, so the design makes this harder to fix. Fix: key totals by `customerId` and add the names at the end.
3. **One name lookup per order, one after another** (`:50-53`). Each order waits for its lookup before the next one starts, and repeated customers are looked up again. 10,000 orders from 50 customers means 10,000 serial calls where 50 concurrent ones would do. Fix: collect the unique ids, then run `Promise.all` into a `Map`.

### Medium
4. **The aggregation is O(orders × customers)** (`:18`). `rows.find` scans the whole list on every `add`. Use a `Map`.
5. **Every order is held in memory before aggregation starts** (`:38-42`). Totals could be built page by page instead. Separately, `push(...items)` can throw a `RangeError` if a single page is extremely large; that's unlikely with normal page sizes.
6. **Any status other than `'paid'` is subtracted** (`:17`). This depends on the `pending` filter on line 51. If the API starts sending a new status (such as `'void'`), it gets subtracted as if it were a refund. Fix: handle each status explicitly in a `switch` with a `never` exhaustiveness check.
7. **The aggregator abstraction may be unneeded** (`:8-30`, `:36`). `OrderAggregator`, `createAggregator` and the `opts.aggregator` option exist for one implementation, which goes against the project's YAGNI rule. This is debatable: the injection point could be intended for dependency injection.
8. **Type surface** (`:33-37`, `:2`). `summarizeOrders` has no return type annotation, which the conventions require for exported functions. `Page` is used in the exported signature but isn't exported itself.
9. **No tests.** The README says tests live in `test/`, but that directory doesn't exist.

### Low
- `x2` (`:17`) is a meaningless name; `signedAmountCents` would be clearer.
- Line 45 logs a failure at `info` level and uses `String(err)`, which drops the stack and `cause`. The `Logger` interface has no `warn` or `error` method.
- Long-running pagination can't be cancelled because there's no `AbortSignal` support.

### Possible issues, depending on how the data behaves
- **Infinite loop:** if `fetchPage` repeats a `nextPage` value, the loop never ends and memory keeps growing. There's no visited-page check or page limit.
- **Refund records:** if a refunded order is the original sale record with its status changed, rather than a separate refund record, the code subtracts money that was never added. Check this against the API contract.
- **Bad amounts:** `amountCents` isn't checked. A negative or fractional amount would quietly corrupt the totals, and `NaN` would also break the sort on line 24.
- **Unstable order:** customers with equal totals keep first-seen order, which depends on page order. If you need deterministic output, add a tiebreaker.
