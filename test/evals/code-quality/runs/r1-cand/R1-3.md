The ts-code-reviewer agent reviewed the whole of `src/orders.ts` (55 lines, no imports) against the project's `.claude/rules`. I re-read the file myself to check its claims, and the line references below are correct. No files were edited.

**Checks that didn't run:** `tsc` (TypeScript isn't installed in the project) and tests (the `test/` directory the README describes doesn't exist). No linter or formatter is configured.

## Critical
1. **A failed page fetch silently cuts the results short** (`src/orders.ts:44-47`). If `fetchPage` throws, the code logs it at `info` with `String(err)`, which drops the stack, and stops paging. The caller gets totals from only the pages that loaded, with no sign anything is missing. If page 1 fails, the result is `[]`, which looks the same as "no orders". With no logger passed in, there's no trace at all. **Fix:** rethrow with `{ cause: err }`, or return a typed partial result.

## High
2. **Totals are grouped by customer name, not ID** (`:18`). Two different customers named "John Smith" get merged into one row. The TSDoc on `:32` says "per customer name", so either the spec intends this or the spec is wrong too. Worth confirming.
3. **One name lookup per order, one after another** (`:50-53`). `await lookupCustomerName` inside the loop makes one call per order and never deduplicates. 10k orders from 50 customers means 10k serial calls instead of 50 concurrent ones. **Fix:** collect the distinct IDs, then `Promise.all`.
4. **The two kinds of failure are handled differently** (`:52` vs `:44`). A failed page is swallowed, but a single failed name lookup rejects the whole call after every page has already been fetched.

## Medium
5. **Each `add()` searches the whole row list** (`:18`): `rows.find` makes aggregation O(orders × customers). Use a `Map`.
6. **Every page is held in memory before processing starts** (`:38-43`), including pending orders that get thrown away. Aggregate each page as it arrives instead.
7. **`all.push(...result.items)` can throw a `RangeError` on very large pages** (`:42`). Because it's inside the `try`, it's treated as a page failure and the data is cut short as in #1. Plausible, but depends on page size.
8. **Nothing stops the loop if the backend misbehaves** (`:39-48`). A repeated `nextPage` loops forever. There's no maximum page count and no `AbortSignal`. Plausible.
9. **Every status other than `'paid'` is subtracted** (`:17`). If the API starts sending an unexpected status such as `'cancelled'`, it's silently counted as a refund, because the data is never validated. Plausible, since it depends on runtime data.
10. **The `OrderAggregator` interface is a mutable strategy with only one implementation** (`:8-13, :36, :49`). If a caller reuses an aggregator they passed in, the second call double-counts. The interface also bakes name-based grouping into the public API.
11. **The exported function's signature is incomplete** (`:2, :33-37`). It has no declared return type, and `Page` isn't exported, so callers can't name it.

## Low
12. **`result()` returns the internal row objects** (`:24`). Callers that mutate them change the aggregator's state.
13. **A 0-cent refund gives `-0`** (`:17`), which fails `assert.deepStrictEqual` against `0`.
14. **The name `x2` says nothing** (`:17`). Something like `signedAmountCents` would be clearer.

**Verdict:** not ready as written. The main fixes overlap: group by `customerId` in a `Map` while processing pages as they arrive, look up names once per ID concurrently, and stop swallowing fetch errors.
